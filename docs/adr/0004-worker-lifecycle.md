# ADR 0004: worker のライフサイクルは 1 PR で閉じる

- 状態: 決定（2026-08-30）

## 背景

初版は worker を「担当リポジトリの担当者」として設計していた。命名も `work-<短縮>-<リポジトリ名>`、
worktree も `worktrees/<リポジトリ名>` と、**担当**に紐づけていた。

長いタスクを実際に走らせたところ、この前提が崩れた。1 つのタスクの中で作業の性質が何度も変わり、
同じ worker に別件を積み続けることになる。あるタスクでは 1 人の worker が
「既存実装の評価 → OSS 公開の準備 → ドキュメントの英語化 → スキーマ設計」を順に担当した。

観測されたこと。

- **コンテキストが膨れる。** 再起動時点で 575k トークン（コンテキストの 57%）に達し、
  「full session を再開すると利用枠を大きく消費する」という警告に当たった。
  もう 1 人も 319k トークンだった。要約から再開したところ 10% / 13% に落ちた
- **名前が実体からずれる。** 評価を終えた `work-<...>-eval` がスキーマを設計していた
- **指示ファイルが 1 本のログになる。** 依頼を追記し続けた結果、
  **新しく立てた worker がどれが現在の担当か判別できない。**
  「指示ファイルが唯一の引き継ぎ」（ADR 0003）という前提がここで崩れる

## 決定

**worker のライフサイクルを 1 PR の単位で閉じる。**

```
1 PR = 1 ブランチ = 1 worktree = 1 tab = 1 worker = 1 指示ファイル
```

- PR を出したら（またはその単位の作業が終わったら）**worker・tab・worktree をまとめて閉じる**
- 次の単位は新しく作る。worker を使い回さない
- 命名は**担当ではなく作業単位**（ブランチ名）から導く（→ SKILL.md 命名規則）
- 指示ファイルは作業単位ごとに 1 つ。**自己完結させ、「この 1 件だけがあなたの担当である」と明示する**。
  過去の経緯は `PROGRESS.md` を読ませる
- 「11. 片付け」をタスクの最後ではなく **PR ごとに**適用する形になる

## 帰結

- コンテキストが作業単位を超えて膨らまない
- 名前が実体と一致し続ける
- 新しく立てた worker が、自分の担当を 1 ファイルで把握できる
- **継続性は捨てる。** テストベッドを熟知した worker に差し戻すと即座に直る、という利点は失う。
  読み直しのコストは掛かるが、数十万トークンを抱え続けるより安い。
  そもそも継続性に頼らないことが ADR 0003 の趣旨である
- coordinator は PR ごとに片付けを行うため、タスク終了時に残る後片付けが減る
