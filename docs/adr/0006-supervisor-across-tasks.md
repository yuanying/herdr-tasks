# 0006. 全タスクを束ねる supervisor を置き、STATE.md に状態行を持たせる

- Date: 2026-10-23
- Status: Accepted

## Context

herdr-tasks は 1 タスク = 1 workspace で coordinator を常駐させる（ADR 0002）。
呼び出し元はタスクを渡したら手を引き、以降の進捗は coordinator が持つ。
1 つのタスクについてはこれで閉じている。

タスクが増えると、閉じていないものが見えてきた。

- `~/.local/state/herdr-tasks/` のタスクディレクトリは 27 件を超えた。ユーザーは
  **どれが走っていて、どれが判断待ちで、どれが止まっているか** を一望できない。
  見るには、workspace を 1 つずつ覗くか、`STATE.md` を 1 つずつ開くしかない。
- 止まっているタスクは、止まっていると分からない。coordinator のプロセスが失われると、
  記録は未完のまま、進める者がいなくなる。ADR 0005 で入口を置き、セッションのクリアには
  自力で戻れるようにしたが、**プロセスそのものが失われた場合は人が気づくまで止まる。**
- **タスク同士の関係を置く場所が無い。** あるタスクが別タスクの PR マージを待つ、
  複数のタスクが同じリポジトリやクラスタを触る、完遂したタスクの申し送りが次のタスクに
  引き取られないまま残る。各 coordinator は自分のタスクしか見ていないため、
  どのタスクディレクトリにも書けない。
- 機械的に集計しようにも、**`STATE.md` の書式が揃っていない。** 見出しは `# STATE` /
  `# 状態` / `# STATE: <タスク名>` とまちまちで、状態表の列も、完遂の書き方
  （「最終更新: …（完遂）」、本文中の「全作業単位が完了し」）も違う。
  `TASK.md` も `STATE.md` も無い、herdr-tasks の外で作られたディレクトリも混ざっている。

## Decision

### 1. supervisor ロールを置く

- coordinator を束ねる **supervisor** を、全体で 1 つだけ常駐させる。agent 名は `supervisor`、
  workspace ラベルは `herdr-supervisor`。手順書は `supervisor.md`。
- 責任は 4 つに限る。全タスクの一覧化、タスク横断の管理（依存・衝突・申し送り）、
  新規タスクの起動（`SKILL.md` の呼び出し元を担う）、介入（要判断への回答の取り次ぎと、
  停止した coordinator の立て直し）。
- **supervisor はやらない。** 実装しない。worker に直接触らない（coordinator 経由のみ）。
  coordinator の代わりに判断しない。マージしない。ADR 0005 で coordinator に課した
  「実装しない」を一段上にも適用する。束ねる側が手を出し始めると、
  タスクの記録と実体の整合を誰が保っているのかが曖昧になる。
- 取り次ぎ・立て直し・新規タスクの起動は、**ユーザーの確認を取ってから** 行う。
  どれもタスクの進行を変えるからである。

### 2. 専用ディレクトリはタスクディレクトリの親の外に置く

- 推奨は `~/.local/state/herdr-supervisor/`。`~/.local/state/herdr-tasks/` の中には置かない。
  supervisor はそこを走査して一覧を作るため、中に置くと自分自身がタスクとして混ざる。
- `scripts/write-supervisor-agents.sh` は、指定されたディレクトリがタスクディレクトリの親の
  中にあれば拒否する。推奨を規約ではなく構造で担保する。

### 3. 入口は ADR 0005 と同じ方式で生成する

- supervisor ディレクトリに `AGENTS.md` と、それを `@` で読み込むだけの `CLAUDE.md` を置く。
  雛形は `templates/supervisor-agents.md`、生成は `scripts/write-supervisor-agents.sh`。
- 手書きファイルを上書きしない判定と `CLAUDE.md` の生成は `scripts/lib/agents-entry.sh` に
  切り出し、`write-task-agents.sh` と共有する。2 つの入口で冪等性の規律が食い違わないようにする。
- 中身は入口に徹する。読むべき手順書と、全タスクディレクトリの親のパスだけを置く。

### 4. 記録は変更頻度で 3 つに分ける

`coordinator.md` 手順 3 と同じ切り方を supervisor にも適用する。

| ファイル | 持つもの | 書き換わり方 |
|---|---|---|
| `BOARD.md` | 全タスクの一覧 | 聞かれるたびに作り直す |
| `RELATIONS.md` | いま有効なタスク横断の関係 | 関係が変わるたびに上書き |
| `LOG.md` | 介入・起動・関係の発見と解消 | 追記のみ |

- **タスクの状態の正は各タスクの `STATE.md` と herdr の実体に置き、supervisor は持たない。**
  `BOARD.md` は毎回ゼロから導く派生物である。タスクの状態を supervisor 側にも正として持てば、
  coordinator が更新するたびに食い違う。作り直す前提の一覧なら、古くなっても誰も誤らせない。
- **タスクをまたぐ関係だけは supervisor が正を持つ。** どのタスクディレクトリにも置き場が
  無いからである。これが `RELATIONS.md` であり、起動時に必ず読むのはこれだけになる。
- 一覧は `$TASKS_ROOT` を走査して作る。登録簿を別に持たない。supervisor が起動したタスクも、
  人が直接立てたタスクも、同じ経路で一覧に載る。**登録の手間が無いので、登録漏れも無い。**

### 5. 監視はユーザーに聞かれたときだけ行う

- supervisor は coordinator に `herdr agent wait` を張らない。一覧も聞かれたときにだけ作る。
- 要判断になった coordinator は自分で通知を出す（`coordinator.md` 手順 7）。
  supervisor が常時見張っても、その通知を二重にするだけである。代わりにタスクの数だけ
  待機を抱え、supervisor のコンテキストを一覧の作り直しで埋めていく。
- 停止中のタスクに気づくのは、ユーザーが一覧を求めたときになる。停止を即座に拾う仕組みは
  置かない。拾うべき停止は「進める者がいない」状態であり、急ぐものではない。

### 6. STATE.md の 1 行目に状態行を必須にする

- `STATE.md` の 1 行目を `状態: 進行中|要判断|完遂|中止` とする。値はこの 4 つだけ。
- 呼び出し元は枠を作るときに `状態: 進行中` を入れる。以降は coordinator が、状態が
  変わったのと同じターンで上書きする。`要判断` は「未解決の要判断」が空でないことと常に一致させる。
- 1 行目に固定するのは、supervisor が `head -n 1` だけで全タスクを分類できるようにするためである。
  本文から状態を推定させると、何十件もの本文を毎回読ませることになり、推定を誤る余地も残る。
- 分類は状態行と coordinator の在否の組み合わせで決める。`進行中` / `要判断` なのに
  cwd がタスクディレクトリと一致する agent がいなければ、**停止中** とする。

### 7. supervisor は既存タスクの STATE.md を書き換えない

状態行の無い既存タスクには、supervisor が状態行を書き足す案もあった。採らない。

- `STATE.md` は coordinator が毎回まるごと上書きするファイルである。外から足した行は、
  次の上書きで消えるか、coordinator の書いた内容と食い違う。**書き手が 2 人いる
  上書きファイルは、どちらの記録も信用できなくなる。**
- 状態行の無いタスクは、supervisor が中身を読んで推定し、一覧に「（推定）」と明記する。
- 状態行は、そのタスクの coordinator が次に `STATE.md` を上書きするときに入る
  （`coordinator.md` 手順 1）。停止中のタスクを supervisor が立て直せば、再開判定の中で入る。
- supervisor がタスクディレクトリに書き込むのは、呼び出し元として新しいタスクを用意するとき
  だけである。coordinator に引き渡した後は書かない。タスク横断の情報は coordinator に
  取り次ぎ、記録するかどうかは coordinator が決める。

## Consequences

- ユーザーは supervisor に聞くだけで、全タスクの状態と、タスクをまたぐ関係を一度に見られる。
- **止まったタスクが見える。** 状態行と coordinator の在否を突き合わせるため、
  記録を揃えたまま止まっているタスクが「停止中」として浮かぶ。立て直しは `SKILL.md` の
  既存の再開手順で行い、supervisor 専用の復旧経路は作らない。
- 状態行の無い既存タスクは、coordinator が再び動くまで推定のまま残る。すでに完遂して
  coordinator のいないタスクは、ずっと推定で一覧に載る。推定の手間は毎回掛かるが、
  `STATE.md` の書き手を 1 人に保つことを優先した。
- 停止の発見は、ユーザーが一覧を求めるまで遅れる。常時監視を置かない代わりの対価である。
- coordinator には「supervisor からの取り次ぎ」を受ける規定が増えた（`coordinator.md` 手順 7）。
  取り次がれた情報を記録するのは coordinator であり、記録しなければタスクには残らない。
- 状態行の値は 4 つに固定した。「マージ待ち」や「片付け待ち」は値に持たせず、
  一覧の要点に書く。値を増やすと、coordinator が直し忘れる遷移が増える。
- 入口の生成処理を共有したため、マーカー行の形式を変えるときは 2 つの入口に同時に効く。
  既存の生成物との互換を壊さないよう、マーカーの先頭は変えない。
