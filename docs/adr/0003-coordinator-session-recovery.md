# 0003. coordinator の会話文脈が失われても再開できる状態をタスクディレクトリに残す

- Date: 2026-08-21
- Status: Accepted（2026-09-02 に追記あり。末尾の「追記」を必ず読む）

## Context

coordinator は agent プロセスであり、セッションのクリア・コンテキスト溢れ・プロセス停止で
会話文脈を失う。ADR 0001 の時点から「coordinator と worker の間で渡せるのはファイルのパスだけ」
という制約は認識していたが、同じ制約が **停止前の coordinator と再開後の coordinator の間** にも
成り立つことを扱っていなかった。

TASK_DIR は固定パスに残るため、TASK.md・PROGRESS.md・notes/・worktree・branch は生き残る。
しかし再開に必要な次の事実は、これまで coordinator の会話文脈にしか存在しなかった。

- 各 worker に渡した指示の本文（担当範囲・依存・前提）。PROGRESS.md には worker 名しかないため、
  再開後は差し戻しも再送もできない。
- 検証時の比較起点となる base コミット。「デフォルトブランチの最新」は時間で動くため、
  再開後に同じ差分を再現できない。
- スキルのパス、agent kind、workspace ID。worker を立て直すときに必要になる。
- エスカレーションの有無。ユーザーへ何を問い合わせて待っているのかが失われる。

さらに PROGRESS.md を副作用の後に更新する規律では、tab 作成から記録までの間に停止すると、
記録に無い worktree や tab が残り、再開した coordinator がそれを認識できない。

## Decision

- 再開に必要な事実は、すべて TASK_DIR 配下のファイルに置く。coordinator の記憶を前提にしない。
- 保存先は既存の TASK.md と PROGRESS.md を拡張して賄い、機械可読な状態ファイルは別に持たない。
  人間が読む記録と再開に使う記録を二重管理しないことを優先する。
- PROGRESS.md の状態表に、base コミット・agent kind・差し戻し回数を項目として加える。
- TASK.md に「実行環境」の節を設け、スキルのパス・agent kind・workspace ID を記録する。
- worker への指示は `notes/workers/<worker 名>.md` に書いてから渡し、プロンプトではそのパスを参照する。
  差し戻し・再送・再開はすべて同じファイルを起点にする。
- PROGRESS.md は write-ahead で更新する。worktree・tab・agent を作る前に意図を書き、
  作成後に応答から得た ID を埋める。これにより「記録はあるが実体がない」「実体はあるが記録がない」の
  両方を再開時に検出できる。
- coordinator は起動時にまず再開かどうかを判定する。PROGRESS.md の記録と、worktree・tab・agent の
  実在を突き合わせ、生存している worker には再接続し、失われた worker だけを立て直す。

## Consequences

- coordinator は停止しても、同じ workspace で agent を起動し直して手順書とタスクディレクトリを
  読ませれば作業を継続できる。呼び出し元の会話文脈も不要になる。
- 状態表の項目が増え、coordinator が書く量と更新の手間が増える。write-ahead により、
  実体を作らずに終わった行が一時的に残ることも許容する。
- 記録は自然言語のままなので、再開時の突き合わせは coordinator の読み取りに依存する。
  厳密な機械処理が必要になった場合は、この判断を見直して状態ファイルの導入を再検討する。
- worker への指示がファイルとして残るため、タスク完了後もどの範囲を誰に任せたのかを追跡できる。

## 追記 (2026-09-02): 置いた記録は腐る

### 何が起きたか

この ADR の後、coordinator のセッションが何度も切れる長いタスクを走らせた。
タスクディレクトリは残り、再開そのものは機能した。**残っていた記録の中身が現実とずれていた。**

- **TASK.md が陳腐化した。** 呼び出し元が最初に書いたまま 10 日以上更新されず、
  その間に 4 件の決定がそこに書かれた前提（対象リポジトリ、設定スキーマの中心となる型、
  型の数、既存実装を採るか自作するか）を覆していた。**どれも「確定」と書いてある。**
  再開した coordinator は、間違った前提を自信を持って読む。
- **PROGRESS.md の状態表が沈んだ。** 追記しか規定していないため時系列が 1300 行に伸び、
  状態表が中ほどに埋もれた。古い節は当時の現在形で書かれているため、
  **どれがいまの話なのかが読み取れない。** 再開手順は PROGRESS.md 全体を読ませていた。
- **worker の完了報告が coordinator に届かなかった。** worker は報告を自分の pane に出して終わり、
  coordinator はそれを知らずに「作業中」のまま待っていた。

### なぜ起きたか

この ADR は「再開に必要な事実をファイルに置く」ことを決めたが、
**置いたものが古くなったときに誰が直すのかを決めていなかった。**

記録は書いた時点では正しく、決定が進むごとに現実から離れる。訂正の担い手が居なければ、
「再開に必要な事実」は時間とともに「再開を誤らせる事実」に変わる。しかも記録があるぶん、
何も無い場合より悪い。読み手は書いてあるものを疑わない。

もう 1 つ、この ADR は **記録を役割で 2 つに置いた**（仕様は TASK.md、進捗は PROGRESS.md）が、
**変更頻度が違うものを 1 つのファイルに同居させていた。** 状態表は毎回書き換わり、
時系列は追記しかしない。同居させると、書き換わる部分が伸び続けるファイルの中に沈む。
「先頭だけ読む」と規約に書いても、それは読み手の規律に頼るだけで、構造は何も止めていない。

### 追加で決めたこと

**1. 記録を変更頻度で 3 つに分ける。**

| ファイル | 持つもの | 書き換わり方 | 再開時 |
|---|---|---|---|
| `TASK.md` | ゴール・制約・実行環境と、覆った前提の訂正（「現在地」節） | まれ | 必ず読む |
| `STATE.md`（新設） | 状態表・次にやること・未解決の要判断 | 毎回上書き | 必ず読む |
| `PROGRESS.md` | 日付つきの時系列 | 追記のみ | 必要なときだけ |

必ず読む 2 つが小さいまま保たれ、無制限に伸びるものは読まなくてよくなる。
**規約ではなく構造で担保されるのが、この形を選ぶ理由である。**

**これは「機械可読な状態ファイルを持たない」という当初の判断を覆すものではない。**
`STATE.md` は YAML でも JSON でもなく、人が読む同じ自然言語の記録である。
分ける理由は形式ではなく**変更頻度**であり、当初が避けたかった「人間が読む記録と
再開に使う記録の二重管理」は起きない。どちらも人間が読む記録のままである。

**2. 二重管理を境界で潰す。** 分けた以上、同じことを二か所に書けば、いずれ片方だけが
更新されて食い違う。`STATE.md` にはいまの事実だけ、`PROGRESS.md` には起きたことだけを書き、
同じ結論を両方に書かない。なぜそうなったかは STATE.md から日付で PROGRESS.md を引く。

**3. 訂正に持ち主を与える。** 決定が TASK.md に書かれた前提を覆したら、
**覆した coordinator がその場で**冒頭の「現在地」節を直す。本文と付録は残し、
現在地が本文と付録より優先することを節自身に書く。「現在地」の枠は、呼び出し元が
TASK.md を書く時点で空のまま置く。直す先が無ければ直されない。

**4. PROGRESS.md を刈れるようにする。** 分けても追記は伸びる。溜まるものは 2 種類で、
決定・実測・踏んだ落とし穴は残し、運用の足跡（worker を立てた、tab ID、base SHA、片付けた）は
**その作業単位が閉じた時点で価値がゼロになる**ため消してよい。刈るのは片付け（手順 11）のとき。
**日付でローテーションしない** —— 古い分をまとめて流すと、残すべきものまで一緒に流れる。
迷ったら残す。重い決定は PROGRESS.md に置かず、対象リポジトリの ADR へ昇格させる。

**5. 報告を二重に担保する。** worker の完了報告とエスカレーションは、coordinator に届く手段が
あるならそれで送る。coordinator 側の完了待ちと合わせて両方で担保する。完了待ちは報告せずに
終了した worker を拾い、報告は blocked で止まった worker を拾う。片方だけでは取りこぼす。

### 帰結

- 再開時に必ず読む量が、タスクの長さに比例しなくなる。ここが当初の形との一番の違いである。
- ファイルが 1 つ増え、書き分けの判断が要る。境界を 3 つの規則で一意に決めることで、
  「どちらに書くか」を毎回考えなくて済むようにした。
- 「現在地」と本文、`STATE.md` と `PROGRESS.md` は、どちらも二重に読めば矛盾して見える。
  優先順位と境界を規約に明記することで解決する。**優先順位を書かない記録は、
  読み手にどちらが新しいかを推測させる。**
- 当時の判断が読めなくなることは避けたいので、**古い記述は消さずに残す。**
  古い記述は誤りではなく、当時の判断の記録である。誤りになるのは、
  それが最新であるかのように読まれたときだけである。
- 刈り込みを規約にしたことで、経緯を失う危険が新しく入った。「迷ったら残す」と
  「重い決定は ADR へ昇格」で釣り合いを取る。
